Project Architecture

How the educational site, R infrastructure, validation system, and generated outputs work together

A technical reference for the repository structure, reproducible execution, modular R design, source catalogs, validation contracts, provenance, outputs, continuous integration, versioning, and extension of the NHANES Laboratory Data with R project.
Repository design · reproducibility · validation

A clear separation between learning content, executable infrastructure, and research outputs.

This page explains how the NHANES Laboratory Data with R project is organized technically. It focuses on repository structure, reproducible execution, modular R code, validation contracts, provenance, output management, testing, versioning, and extension.

Educational layer Foundations, laboratory guides, pipeline catalogs, and structured courses
Execution layer Configuration files, R functions, scripts, validation rules, and tests
Output layer Processed datasets, tables, figures, logs, and provenance records

Purpose of this page

The rest of the website explains:

  • how NHANES is structured;
  • how laboratory data should be interpreted;
  • how survey design and weights work;
  • how cycles are combined;
  • how specific analytical pipelines are built.

This page does not repeat those topics.

Its purpose is to explain:

how the repository itself works

and:

how the technical design supports reproducibility

The project architecture

Configure Declare sources, cycles, roles, and expectations.
Acquire Download and preserve official public-use files.
Validate Check structures, keys, rows, variables, and relationships.
Transform Harmonize, combine, merge, label, and document.
Publish Create datasets, tables, figures, lessons, and evidence.

The exact files may grow over time, but the architectural roles should remain distinct.

What each layer does

1

Website configuration

`_quarto.yml` defines navigation, sidebars, page order, rendering behavior, and the overall website structure.

2

Source configuration

Files under `config/` declare official source files, cycles, URLs, roles, expected structures, and local destinations.

3

Reusable R modules

Files under `R/` contain focused functions for catalog handling, acquisition, validation, integration, and output generation.

4

Execution scripts

Files under `scripts/` provide controlled entry points that run the pipeline in a defined order.

5

Research data

Raw files are preserved separately from processed datasets so source evidence is not confused with derived analytical products.

6

Generated outputs

Tables, figures, validation records, logs, and provenance manifests are written to dedicated output folders.

Website and pipeline execution are separate

The Quarto website and the analytical pipeline serve different purposes.

  • Website rendering
  • Pipeline execution
  • Why the separation matters

Quarto processes .qmd files and produces HTML pages.

Typical command:

quarto render

This builds the website.

It should not silently:

  • install analytical packages;
  • refresh source data;
  • overwrite research datasets;
  • change raw files;
  • rerun long network-dependent workflows.

The R pipeline performs the data work.

A repository-level entry point may resemble:

Rscript scripts/run_pipeline.R

Depending on implementation, optional arguments may control:

  • source refresh;
  • CSV exports;
  • validation strictness;
  • output destinations;
  • logging behavior.

Separating rendering from analytical execution makes it easier to:

  • preview documentation without rerunning the pipeline;
  • review website changes independently;
  • avoid unintended data modification;
  • keep network failures from breaking ordinary documentation work;
  • reproduce outputs through an explicit command.

Architecture rule: Rendering documentation should not silently mutate research data.

Reproducible software environment

The project uses a recorded R environment so package versions can be restored.

A typical restoration command is:

Rscript -e 'renv::restore()'

The lockfile records the package environment expected by the project.

Important files may include:

renv.lock
renv/
.Rprofile

A reproducible environment helps reduce differences caused by:

  • package updates;
  • changed defaults;
  • dependency conflicts;
  • machine-specific library states;
  • inconsistent development environments.

Configuration-driven acquisition

Every upstream file should be declared in a structured source catalog rather than being scattered across scripts.

The catalog may include:

survey_cycle
component
file_name
file_role
source_url
local_path
expected_rows
record_level
merge_key
required_variables
notes

A configuration-driven approach provides:

  • one auditable source list;
  • explicit cycle coverage;
  • controlled primary and supplementary roles;
  • reusable acquisition logic;
  • easier extension to additional components.
ImportantAdding a catalog row is not enough to support a new analysis

A new source also requires:

  • record-level validation;
  • variable review;
  • eligibility documentation;
  • merge logic;
  • method review;
  • survey-weight guidance;
  • analytical tests.

Modular R architecture

A modular design separates responsibilities.

`catalog.R`

Reads, validates, filters, and documents the source catalog.

`download.R`

Downloads files, records status, calculates hashes, and preserves raw sources.

`validate.R`

Checks files, variables, dimensions, keys, duplicates, and expected relationships.

`pipeline.R`

Coordinates import, harmonization, integration, analysis, and output creation.

The main entry script should coordinate these modules rather than contain every implementation detail.

A simplified pattern is:

source(
  file.path(
    "R",
    "catalog.R"
  )
)

source(
  file.path(
    "R",
    "download.R"
  )
)

source(
  file.path(
    "R",
    "validate.R"
  )
)

source(
  file.path(
    "R",
    "pipeline.R"
  )
)

run_pipeline()

Why modularity matters

Modular functions make it easier to:

  • test one responsibility at a time;
  • reuse logic across pipelines;
  • isolate failures;
  • improve code review;
  • add new laboratory components;
  • avoid duplicating validation code;
  • preserve a readable execution sequence.

Validation contracts

A validation contract is an explicit condition that must be true before the pipeline continues.

Examples include:

required file exists
expected variables are present
participant keys are complete
primary records are unique
row counts are plausible
join relationships are valid
output files were created

Source contract

The expected file exists, imports successfully, and matches the declared source role.

Schema contract

Required variables, classes, labels, and identifiers are present.

Key contract

Participant keys are complete and unique where one-row-per-person structure is required.

Merge contract

The join preserves the intended analytical population and expected row count.

Output contract

Required datasets, tables, figures, logs, and validation records are created.

Architecture rule: A pipeline should stop when an essential contract fails rather than silently create a questionable dataset.

Component-specific validation

Not every NHANES file has one row per participant.

Some components may contain:

  • repeated examinations;
  • food-level records;
  • medication-level records;
  • event-level observations;
  • multiple specimens;
  • replicate measurements.

Therefore, validation rules must reflect the declared record level.

A generic uniqueness rule applied to every component would be incorrect.

Provenance and source integrity

Each run should preserve enough information to establish:

what source was used
when it was obtained
whether it changed
how it was processed
which outputs were generated

A provenance manifest may contain:

source URL
retrieval date and time
local path
file size
SHA-256 hash
imported row count
imported column count
survey cycle
component
file role
pipeline version

File hashes

A cryptographic hash provides a reproducible fingerprint of a file.

For example:

SHA-256

If the same source filename later produces a different hash, the upstream file may have changed.

That change should be reviewed rather than ignored.

WarningA stable URL does not guarantee stable content

Public-use files may be revised while retaining the same general location or name.

Hashes and dimensions help detect upstream changes.

Raw and processed data must remain separate

The project should maintain a clear distinction:

data/raw/

contains downloaded source files.

data/processed/

contains derived and reusable analytical datasets.

Raw files should not be manually edited.

Transformations should be implemented in code and reflected in processed outputs.

  • figure source data;
  • variable dictionaries.

  • row-count reports;

RDS and CSV outputs

RDS and CSV files serve different purposes.

RDS

RDS can preserve:

  • factor structure;
  • variable classes;
  • labels;
  • attributes;
  • R-specific objects.

CSV

CSV supports:

  • portability;
  • review outside R;
  • use in other analytical tools;
  • simple archival inspection.

The pipeline may treat RDS as the primary reusable format and generate CSV copies only when requested.

Controlled execution

A complete run should be initiated explicitly from the repository root.

A general command may resemble:

Rscript scripts/run_pipeline.R

A configurable entry point may support options such as:

Rscript scripts/run_pipeline.R \
  --refresh=true \
  --write-csv=false

The exact arguments must match the implementation in the repository.

Continuous integration

Continuous integration can test the repository automatically when code changes.

Useful checks include:

  • R syntax;
  • function tests;
  • synthetic-data tests;
  • configuration validation;
  • expected output structure;
  • Quarto rendering;
  • broken links;
  • reproducibility checks.

Network-dependent source refreshes should usually be separated from ordinary pull-request tests.

This prevents temporary upstream outages from making every code review unreliable.

Scheduled refreshes

A scheduled workflow may:

  • check official sources;
  • download updated files;
  • compare hashes;
  • inspect row counts;
  • detect revisions;
  • create a report;
  • require human review before accepting upstream changes.

The pipeline should not silently approve a changed upstream file simply because the download succeeded.

Versioning and releases

A reproducible analysis should identify the exact project version used.

Versioning may include:

  • Git commit;
  • release tag;
  • pipeline version;
  • source manifest;
  • package lockfile;
  • output date;
  • provenance file.

A formal release may contain:

source code
documentation
citation metadata
license
release notes
validation summaries

Citation

The project should provide a machine-readable citation file such as:

CITATION.cff

A complete analytical report should cite:

  • the project version;
  • the original CDC or NCHS data sources;
  • the survey cycles used;
  • the source files or components;
  • the provenance manifest;
  • the relevant NHANES documentation.

Extending the repository

Adding another laboratory pipeline should follow a controlled sequence.

1

Declare sources

Add reviewed source files, URLs, cycles, roles, expected variables, and record levels.

2

Model the records

Establish what one row represents and which keys define uniqueness.

3

Review compatibility

Assess units, methods, eligibility, detection limits, and cycle differences.

4

Define validation

Create component-specific schema, key, range, missingness, and merge checks.

5

Document weights

Identify the eligible sample, component weight, cycle adjustment, strata, and PSUs.

6

Publish evidence

Save processed datasets, dictionaries, diagnostics, limitations, and reproducibility records.
