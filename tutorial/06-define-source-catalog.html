Define the NHANES Source-File Catalog

Create a structured manifest describing every CBC and Demographic file used by the pipeline

Build and validate a reproducible source-file catalog for the NHANES CBC and Demographic pipeline.
NoteLearning objectives

By the end of this lesson, you should be able to:

  • explain why a source-file catalog is preferable to scattered filenames;
  • identify the metadata required for every source file;
  • distinguish primary files from supplementary files;
  • assign survey cycles and analytical roles;
  • validate the catalog before downloading data;
  • save the catalog as a reusable CSV file.

What is a source-file catalog?

A source-file catalog is a structured table describing every file used by the pipeline.

Instead of placing filenames and URLs throughout the script, the catalog stores them in one auditable object.

Each row represents one NHANES source dataset.

The production repository uses required catalog fields including:

  • dataset_id;
  • cycle;
  • cycle_start;
  • cycle_end;
  • component;
  • file_id;
  • exam;
  • analysis_role;
  • record_level;
  • merge_key;
  • expected_rows;
  • url.

This structure makes the acquisition process explicit and testable.

Why the catalog matters

A source catalog provides:

  • one authoritative list of source files;
  • explicit survey-cycle labels;
  • official CDC URLs;
  • component classification;
  • primary versus supplementary roles;
  • expected record levels;
  • merge-key documentation;
  • expected row counts;
  • a basis for automated validation.

Without a catalog, source information can become scattered across:

  • download functions;
  • comments;
  • filenames;
  • manual notes;
  • analytical scripts.

Primary and supplementary roles

Primary records

Primary records belong in the main person-level analytical pipeline.

Examples:

  • the standard CBC examination for each cycle;
  • the Demographics file for each cycle.

Supplementary records

Supplementary records are preserved but excluded from the primary person-level stack unless a separate analysis requires them.

The principal example is:

L25_2_B

This is the 2001–2002 second CBC examination.

It is valuable data, but it should not be treated as another independent group of primary participants.

Catalog field definitions

Field Meaning
dataset_id Unique internal identifier for the source row
cycle Human-readable survey-cycle label
cycle_start First calendar year of the cycle
cycle_end Final calendar year of the cycle
component CBC or Demographic component
file_id NHANES source filename without .xpt
exam Primary, second examination, or not applicable
analysis_role Primary or supplementary
record_level What one row represents
merge_key Expected identifier used for integration
expected_rows Expected source row count
url Official CDC download address

Add expected rows and URLs

Expected row counts and official URLs should be maintained as catalog metadata rather than hidden in download functions.

For this guided lesson, create those fields as explicit placeholders that must be populated from the validated project catalog:

nhanes_catalog <- nhanes_catalog |>
  dplyr::mutate(
    expected_rows = NA_integer_,
    url = NA_character_
  )
ImportantDo not invent expected row counts

Expected row counts are validation contracts.

They should come from:

  • the validated repository catalog;
  • a confirmed prior pipeline release;
  • direct inspection of the official source file.

Do not enter guessed row counts merely to make validation pass.

Add:

required_catalog_columns <- c(

  "cycle_end",
  "component",
  "file_id",
  "exam",
  "analysis_role",
  "record_level",
  "merge_key",
  "expected_rows",
  "url"
)

This matches the required structure used by the repository’s catalog validation module.

Validate column names

Add:

missing_catalog_columns <- setdiff(
  required_catalog_columns,
  names(
    nhanes_catalog
  )
)

if (length(missing_catalog_columns) > 0) {
  stop(
    "Catalog is missing required columns: ",
    paste(
      missing_catalog_columns,
      collapse = ", "
    )
  )
}

Validate unique dataset identifiers

Add:

if (anyDuplicated(
  nhanes_catalog$dataset_id
) > 0) {
  stop(
    "Every dataset_id must be unique."
  )
}

Validate cycle years

Add:

if (any(
  nhanes_catalog$cycle_start >
    nhanes_catalog$cycle_end
)) {
  stop(
    "cycle_start cannot be later than cycle_end."
  )
}

Validate analytical roles

Add:

supported_analysis_roles <- c(
  "primary",
  "supplementary"
)

unsupported_roles <- setdiff(
  unique(
    nhanes_catalog$analysis_role
  ),
  supported_analysis_roles
)

if (length(unsupported_roles) > 0) {
  stop(
    "Unsupported analysis roles: ",
    paste(
      unsupported_roles,
      collapse = ", "
    )
  )
}

The production catalog validator supports primary and supplementary analytical roles.

Validate record level

The current CBC pipeline expects person-level source files:

supported_record_levels <- "person"

unsupported_record_levels <- setdiff(
  unique(
    nhanes_catalog$record_level
  ),
  supported_record_levels
)

if (length(unsupported_record_levels) > 0) {
  stop(
    "Unsupported record levels: ",
    paste(
      unsupported_record_levels,
      collapse = ", "
    )
  )
}

The repository deliberately stops when an unsupported record level is introduced without additional validation logic.

Validate the merge key

Add:

if (any(
  nhanes_catalog$merge_key != "SEQN"
)) {
  stop(
    "Every current source file should use SEQN as its source merge key."
  )
}

Validate the number of source rows

Add:

if (nrow(
  nhanes_catalog
) != 21) {
  stop(
    "The CBC and Demographic catalog should contain 21 source rows."
  )
}

Validate the primary and supplementary counts

Add:

primary_source_count <- sum(
  nhanes_catalog$analysis_role == "primary"
)

supplementary_source_count <- sum(
  nhanes_catalog$analysis_role == "supplementary"
)

if (primary_source_count != 20) {
  stop(
    "The catalog should contain 20 primary source files."
  )
}

if (supplementary_source_count != 1) {
  stop(
    "The catalog should contain one supplementary source file."
  )
}

Confirm the second examination is supplementary

Add:

second_exam_check <- nhanes_catalog |>
  dplyr::filter(
    file_id == "L25_2_B"
  )

if (nrow(second_exam_check) != 1) {
  stop(
    "L25_2_B should appear exactly once in the catalog."
  )
}

if (
  second_exam_check$analysis_role !=
    "supplementary"
) {
  stop(
    "L25_2_B must be classified as supplementary."
  )
}

Why URLs are completed separately

The catalog must eventually include validated official CDC HTTPS URLs.

The production validator requires catalog URLs to use the official CDC host rather than an arbitrary or insecure source.

In the next lesson, you will:

  1. generate or populate the official URL for one source;
  2. download one XPT file;
  3. verify the HTTP response;
  4. confirm the local file exists;
  5. read it with haven.

Common mistakes

Duplicate dataset_id

Each catalog row needs a unique internal identifier.

Classifying L25_2_B as primary

The second examination must remain supplementary for the primary person-level workflow.

Omitting the cycle

The cycle is required for:

  • provenance;
  • composite-key construction;
  • cycle-level auditing;
  • output organization.

Guessing expected rows

An inaccurate expected count can cause a valid source to fail or an invalid source to pass.

Using unofficial URLs

The pipeline should retrieve source data from official CDC locations.

Mixing record levels

A source with multiple rows per participant requires additional record-level and join validation.

Knowledge check

NoteWhy use a source-file catalog?

It centralizes source metadata, makes acquisition reproducible, supports validation, and prevents filenames and URLs from being scattered throughout the code.

NoteWhy is L25_2_B classified as supplementary?

It contains a second examination for participants who may already appear in the primary CBC file. It should be preserved separately rather than treated as another independent primary sample.

NoteWhat does record_level = "person" mean?

It means each source row is expected to represent one participant-level record for the specified examination and cycle.
