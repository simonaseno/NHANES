Lesson 12: Merge CBC and Demographic Data Safely

Join the two components using validated participant-cycle keys

Merge the combined CBC and Demographic datasets, validate the join relationship, and troubleshoot duplicated keys, row multiplication, unmatched records, and column conflicts.
NoteLearning objectives

By the end of this lesson, you should be able to:

  • explain why SEQN alone is not the complete cross-cycle merge key;
  • validate key completeness before joining;
  • confirm key uniqueness in both component datasets;
  • identify overlapping non-key column names;
  • perform a one-to-one left join;
  • confirm that the CBC row count is preserved;
  • identify unmatched Demographic records;
  • diagnose row multiplication;
  • investigate duplicated participant-cycle keys;
  • resolve column-name conflicts safely;
  • save a merge-validation report.

Why merge the components?

The CBC files contain laboratory measurements such as:

LBXHGB

The Demographic files contain variables such as:

RIAGENDR
SDMVSTRA
SDMVPSU
survey weights

To analyze hemoglobin by participant characteristics, the two components must be joined.

The intended relationship is:

one CBC participant-cycle record
matched to
one Demographic participant-cycle record

The correct merge key

The merge key is:

c(
  "survey_cycle",
  "SEQN"
)

SEQN identifies participants within NHANES releases.

Because this pipeline combines multiple two-year cycles, survey_cycle is retained as part of the analytical key.

This protects against accidental cross-cycle matches.

WarningDo not join only by SEQN

Even when SEQN appears unique in the combined data, the pipeline should explicitly retain the cycle context.

The intended composite key is:

survey_cycle + SEQN

Where this lesson fits

You should already have:

cbc_primary_1999_2018

and:

demographics_1999_2018

The CBC dataset should contain one primary record per participant and survey cycle.

The Demographic dataset should contain one participant-level record per participant and survey cycle.

Perform the merge

Use the CBC dataset as the left-hand dataset:

cbc_demographics_1999_2018 <-
  cbc_for_merge |>
  dplyr::left_join(
    demographics_for_merge,
    by =
      merge_key,
    relationship =
      "one-to-one"
  )

The left join preserves all primary CBC records.

The relationship = "one-to-one" declaration requires:

  • each CBC key to occur at most once;
  • each matching Demographic key to occur at most once.

If either assumption is violated, the join stops.

If the merge does not work

Use this section immediately when:

  • the join reports an unexpected relationship;
  • the merged row count increases;
  • duplicate keys appear;
  • required variables receive .x and .y suffixes;
  • many CBC records remain unmatched.
WarningDo not remove the relationship check

When relationship = "one-to-one" stops the join, it has identified a key-structure problem.

Do not remove the argument merely to force the merge to complete.

Understand row multiplication

Suppose one CBC key occurs twice and the matching Demographic key also occurs twice.

The join may produce:

2 CBC rows × 2 Demographic rows = 4 merged rows

This is a many-to-many relationship.

The increased row count is not a harmless formatting issue.

It changes the analytical dataset.

Compare key counts directly

Run:

cbc_key_counts <-
  cbc_primary_1999_2018 |>
  dplyr::count(
    survey_cycle,
    SEQN,
    name = "cbc_rows"
  )
demographic_key_counts <-
  demographics_1999_2018 |>
  dplyr::count(
    survey_cycle,
    SEQN,

Join the key counts:

merge_key_relationship_report <-
  dplyr::full_join(
    cbc_key_counts,
    demographic_key_counts,
    by = c(
      "survey_cycle",
      "SEQN"

    cbc_rows =
      dplyr::coalesce(
        cbc_rows,
        0L

    demographic_rows =
      dplyr::coalesce(
        demographic_rows,

      cbc_rows *
        pmax(
          demographic_rows,
          1L

    dplyr::desc(
      expected_join_rows
    )

Do not use distinct() automatically

Avoid:

data |>
  dplyr::distinct(
    survey_cycle,
    SEQN,
    .keep_all = TRUE
  )

This silently keeps one record and discards the others.

Before removing any record, determine whether the duplicates are:

  • exact duplicates;
  • repeat examinations;
  • supplementary records;
  • conflicting observations;
  • records from an incorrectly included source.

Diagnose automatic .x and .y suffixes

After a join, names such as:

source_file_id.x
source_file_id.y

mean that both datasets contained a non-key column with the same name.

Find overlaps:

intersect(
  setdiff(
    names(
      cbc_primary_1999_2018
    ),
    merge_key
  ),
  setdiff(
    names(
      demographics_1999_2018
    ),
    merge_key
  )
)

Rename component-specific columns before joining.

Do not leave ambiguous suffixes in the final analytical dataset.

Confirm that the merge is being performed from CBC

  dplyr::left_join(

Reversing the datasets changes which population is preserved.

merge_validation_summary <-

What success looks like

After this lesson, you should have:

cbc_demographics_1999_2018

The merged dataset should:

  • preserve every primary CBC record;
  • contain at most one Demographic match per CBC record;
  • retain a unique survey_cycle + SEQN key;

  • include a match indicator;
  • retain component-specific provenance;
  • contain no ambiguous .x and .y suffixes.

Common mistakes

Joining only by SEQN

Retain the survey-cycle context.

Ignoring duplicate keys before joining

Duplicate keys can multiply rows.

Removing relationship = "one-to-one"

This hides rather than resolves key-structure problems.

Accepting .x and .y suffixes without review

Rename overlapping provenance columns before the join.

Using an inner join automatically

An inner join removes unmatched CBC records.

The pipeline uses a left join to preserve the primary CBC analytical population.

Treating every unmatched Demographic record as an error

Some Demographic participants may not have a corresponding CBC result.

Using distinct() as a universal duplicate fix

Repeated keys must be investigated before records are removed.

Reversing the left join

The left-hand dataset determines which records are preserved.

Assuming the join is valid because it completes

A join can run successfully and still produce incorrect row counts or relationships.

Checkpoint

Confirm:

Knowledge check

NoteWhy use survey_cycle + SEQN as the key?

The pipeline combines multiple NHANES cycles. Retaining the cycle with the participant identifier makes the cross-cycle analytical key explicit and prevents accidental cross-cycle matching.

NoteWhy specify relationship = "one-to-one"?

It verifies that each CBC key and each matching Demographic key occur no more than once. The join stops when the intended relationship is violated.

NoteWhy use CBC as the left-hand dataset?

The primary analytical population is defined by the validated primary CBC records. A left join preserves those records while adding Demographic information where available.

NoteWhat causes row multiplication?

Row multiplication occurs when one or both datasets contain repeated merge keys. Multiple rows on one side can match multiple rows on the other side.

NoteShould .x and .y suffixes be accepted automatically?

No. They indicate overlapping non-key column names. The meaning of those columns should be reviewed and component-specific variables should be renamed before joining.
