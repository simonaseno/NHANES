Lesson 19: Troubleshoot Common Pipeline Problems

Diagnose download, import, merge, validation, figure, and Quarto errors systematically

Use a structured troubleshooting workflow to identify and resolve common problems in the NHANES CBC and Demographic pipeline.
NoteLearning objectives

By the end of this lesson, you should be able to:

  • distinguish an R pipeline error from a Quarto rendering error;
  • identify the first meaningful error message;
  • confirm that commands are being run from the project root;
  • diagnose package, path, download, and import failures;
  • investigate missing or duplicated participant keys;
  • diagnose row-binding and joining problems;
  • troubleshoot missing analytical variables;
  • troubleshoot figure-generation and figure-embedding problems;
  • inspect failed validation checks;
  • create a reproducible troubleshooting report;
  • know when to stop rather than forcing the pipeline to continue.

Why troubleshooting should be systematic

A long analytical pipeline can fail for many reasons.

The failure may involve:

  • the working directory;
  • a missing package;
  • a malformed source catalog;
  • an unavailable URL;
  • an incomplete download;
  • an invalid XPT file;
  • a missing variable;
  • duplicated keys;
  • incompatible variable classes;
  • an incorrect join;
  • a missing output directory;
  • a failed figure export;
  • a missing embedded image;
  • malformed Quarto YAML;
  • an invalid Markdown structure.

Trying random fixes can make the problem harder to diagnose.

A better approach is:

Identify the first meaningful failure
→ isolate the affected section
→ inspect the relevant object or file
→ correct the underlying cause
→ restart from a clean session
→ rerun the pipeline

The most important troubleshooting rule

ImportantFix the first error first

Later errors are often consequences of the first failure.

For example:

  1. a source file fails to download;
  2. the import object is not created;
  3. the combined dataset is incomplete;
  4. the merge fails;
  5. the figures are not produced;
  6. Quarto cannot find the PNG files.

The original problem is the failed download, not the missing figure.

Distinguish the three systems

This project uses three related but separate systems.

R analytical pipeline

Run with:

Rscript nhanes_pipeline.R

This system:

  • downloads data;
  • imports XPT files;
  • validates records;
  • creates processed datasets;
  • generates tables;
  • generates figures.

Quarto website renderer

Run with:

quarto render

This system:

  • reads .qmd files;
  • processes YAML;
  • converts lessons to HTML;
  • copies figures and supporting files;
  • builds the website.

Quarto preview server

Run with:

quarto preview --port 7841

This system:

  • renders the site;
  • starts a local web server;
  • keeps running until stopped.

A problem in one system does not automatically mean the other systems are broken.

Start with a clean diagnostic sequence

From the project root, run these commands separately.

Confirm the current directory

pwd

The path should end with:

NHANES

Confirm the main files exist

ls -l nhanes_pipeline.R
ls -l _quarto.yml
ls -l tutorial/19-troubleshooting.qmd

Check that R is available

Rscript --version

Check that Quarto is available

quarto --version

Parse the R script

Rscript -e 'parse(file = "nhanes_pipeline.R"); cat("R script parsed successfully.\n")'

Check the Quarto project

quarto check

Do not run all commands in one pasted block when troubleshooting.

Running them separately makes it easier to identify the failing command.

Problem 1: The command is running from the wrong directory

Typical messages

cannot open file 'nhanes_pipeline.R'
No such file or directory
Catalog does not exist
The analysis-ready RDS file does not exist

Diagnose

Run:

pwd

List the directory:

ls

You should see files and folders such as:

_quarto.yml
nhanes_pipeline.R
config
data
outputs
tutorial

Fix

Change into the project directory:

cd /Users/major/Documents/GitHub/NHANES

Confirm:

pwd

Then rerun the failed command.

Why this happens

Relative paths such as:

file.path(
  "data",
  "processed",
  "cbc_demographics_analysis_1999_2018.rds"
)

are interpreted relative to the current working directory.

Problem 2: R cannot parse the script

Typical messages

unexpected symbol
unexpected end of input
unexpected '}'
unexpected string constant

Diagnose

Run:

Rscript -e 'parse(file = "nhanes_pipeline.R")'

R will usually report the approximate line containing the syntax problem.

Inspect the surrounding lines:

sed -n 'START_LINE,END_LINEp' nhanes_pipeline.R

Replace START_LINE and END_LINE with the relevant line range.

For example:

sed -n '420,450p' nhanes_pipeline.R

Common causes

  • missing closing parenthesis;
  • missing closing brace;
  • missing quotation mark;
  • extra comma;
  • incomplete pipe;
  • malformed function call;
  • Markdown code fences copied into the R script;
  • prose copied outside an R comment.

Check for Markdown fences

Run:

grep -n '```' nhanes_pipeline.R

The R script should not contain Quarto code fences.

Fix

Correct the structural syntax problem, save the file, and rerun:

Rscript -e 'parse(file = "nhanes_pipeline.R"); cat("R script parsed successfully.\n")'

Problem 3: A required package is missing

Typical message

there is no package called 'package_name'

Diagnose one package

For example:

Rscript -e 'cat(requireNamespace("haven", quietly = TRUE), "\n")'

Expected:

TRUE

Diagnose all pipeline packages

Run:

Rscript -e 'packages <- c("dplyr","tidyr","purrr","readr","haven","stringr","tibble","ggplot2","digest","httr","scales"); print(data.frame(package = packages, installed = vapply(packages, requireNamespace, logical(1), quietly = TRUE)))'

Fix

Open R:

R

Install the missing package:

install.packages(
  "package_name"
)

Exit R:

q()

Then rerun the package check.

WarningDo not install packages repeatedly inside the production pipeline

Package installation is an environment-setup task.

The production pipeline should validate and load packages, not reinstall them every time it runs.

Problem 4: The source catalog is missing or malformed

Typical messages

Catalog does not exist
Catalog is missing columns
Catalog dataset_id values must be unique
expected_rows must contain positive integers
Unsupported analysis_role in catalog

Confirm the file exists

ls -l config/nhanes_files.csv

Inspect the first lines

sed -n '1,10p' config/nhanes_files.csv

Required catalog columns

The header must include:

dataset_id
cycle
cycle_start
cycle_end
component
file_id
exam
analysis_role
record_level
merge_key
expected_rows
url

Read and validate from R

Run:

Rscript -e 'source("R/catalog.R"); catalog <- read_nhanes_catalog(); print(dim(catalog)); print(names(catalog))'

Check duplicated dataset identifiers

Rscript -e 'x <- read.csv("config/nhanes_files.csv", check.names = FALSE); print(x[duplicated(x$dataset_id) | duplicated(x$dataset_id, fromLast = TRUE), ])'

Check analytical roles

Rscript -e 'x <- read.csv("config/nhanes_files.csv", check.names = FALSE); print(table(x$analysis_role, useNA = "ifany"))'

Expected roles:

primary
supplementary

Check source counts

Rscript -e 'x <- read.csv("config/nhanes_files.csv", check.names = FALSE); print(with(x, table(component, analysis_role)))'

The intended structure is:

10 primary CBC sources
1 supplementary CBC source
10 primary Demographic sources

Problem 5: A download fails

Typical messages

HTTP request failed
Download failed
File size is zero
Source hash could not be calculated

Inspect the acquisition manifest

After a partial run, open:

outputs/validation/acquisition_manifest.csv

From the terminal:

sed -n '1,30p' outputs/validation/acquisition_manifest.csv

Identify failed sources in R

failed_downloads <- acquisition_manifest |>
  dplyr::filter(
    status != "success"
  )

print(
  failed_downloads,
  n = Inf
)

Confirm internet access

Test the official CDC host:

curl -I https://wwwn.cdc.gov/

Inspect one URL

Copy the exact URL from the catalog and run:

curl -I "PASTE_THE_EXACT_URL_HERE"

Check the local file

ls -lh data/raw

A failed download may produce:

  • no file;
  • a zero-byte file;
  • a very small file;
  • an HTML error page saved with an .xpt extension.

Inspect file type

file data/raw/FILE_NAME.xpt

Remove only the failed local file

rm data/raw/FILE_NAME.xpt

Then rerun the acquisition section or the complete pipeline.

Do not replace official URLs casually

A changed URL should be verified against the intended source release before the catalog is modified.

Problem 6: An XPT file cannot be imported

Typical messages

Failed to parse
Unable to read file
Invalid file format
Imported source contains no records

Confirm that the file exists

ls -lh data/raw/FILE_NAME.xpt

Inspect the file type

file data/raw/FILE_NAME.xpt

Test the file directly in R

Rscript -e 'x <- haven::read_xpt("data/raw/FILE_NAME.xpt"); print(dim(x)); print(names(x)[1:10])'

Common causes

  • incomplete download;
  • HTML response saved as XPT;
  • zero-byte file;
  • incorrect catalog URL;
  • corrupted local file;
  • file permission problem.

Fix

Delete the affected local file and download it again.

Do not edit the binary XPT file manually.

Problem 7: SEQN is missing

Typical message

SEQN is missing from a source dataset

Diagnose

Inspect the variable names:

names(
  imported_data
)

Search case-insensitively:

grep(
  "seqn",
  names(
    imported_data
  ),
  value = TRUE,
  ignore.case = TRUE
)

Possible causes

  • the wrong source file was downloaded;
  • the source is not person-level;
  • the source schema differs from the catalog declaration;
  • an HTML file was imported incorrectly;
  • the column was renamed or removed earlier in the pipeline.

Do not create a fake SEQN

The participant key must come from the official source data.

If it is missing, investigate the source rather than generating one.

Problem 8: Duplicate participant keys are found

Typical messages

The combined primary CBC dataset contains duplicate survey_cycle + SEQN keys
The merged dataset contains duplicate keys
Each survey cycle must have exactly one primary CBC source

Identify the duplicated keys

duplicate_keys <- data |>
  dplyr::count(
    survey_cycle,
    SEQN,
    name = "occurrences"
  ) |>
  dplyr::filter(
    occurrences > 1
  )

print(
  duplicate_keys,
  n = Inf
)

Extract affected records

duplicate_records <- data |>
  dplyr::semi_join(
    duplicate_keys,
    by = c(
      "survey_cycle",
      "SEQN"
    )
  ) |>
  dplyr::arrange(
    survey_cycle,
    SEQN
  )

print(
  duplicate_records,
  n = Inf
)

Check source provenance

Inspect:

duplicate_records |>
  dplyr::count(
    survey_cycle,
    source_file_id,
    source_exam,
    analysis_role,
    name = "records"
  )

Check whether L25_2_B entered the primary stack

"L25_2_B" %in%
  unique(
    cbc_primary_1999_2018$source_file_id
  )

Expected:

[1] FALSE

Do not fix with arbitrary deduplication

Avoid:

dplyr::distinct(
  survey_cycle,
  SEQN,
  .keep_all = TRUE
)

The correct response depends on whether the repeated records are:

  • exact duplicates;
  • repeat examinations;
  • complementary records;
  • conflicting values;
  • incorrectly combined sources.

Problem 9: bind_rows() reports incompatible types

Typical message

Can't combine column_name <double> and column_name <character>

Diagnose the variable class by source

purrr::imap_dfr(
  primary_cbc_sources,
  function(
      data,
      dataset_id) {

    tibble::tibble(
      dataset_id = dataset_id,
      variable_class = paste(
        class(
          data$VARIABLE_NAME
        ),
        collapse = "; "
      )
    )
  }
)

Replace:

VARIABLE_NAME

with the actual failing variable.

Inspect values

purrr::imap(
  primary_cbc_sources,
  function(
      data,
      dataset_id) {

    list(
      dataset_id = dataset_id,
      values = unique(
        data$VARIABLE_NAME
      )
    )
  }
)

Possible causes

  • one cycle stores the variable as character;
  • another stores it as numeric;
  • one source contains labelled numeric data;
  • a local transformation changed one source;
  • a metadata column was created inconsistently.

Fix only after reviewing meaning

A conversion such as:

as.numeric()

is appropriate only when the source values are genuinely numeric and the conversion is scientifically justified.

Do not coerce incompatible variables merely to silence the error.

Problem 10: The combined row count is incorrect

Typical message

Combined CBC row count does not equal the sum of its sources

Calculate source rows

source_row_counts <- purrr::imap_dfr(
  primary_cbc_sources,
  function(
      data,
      dataset_id) {

    tibble::tibble(
      dataset_id = dataset_id,
      rows = nrow(
        data
      )
    )
  }
)

Inspect:

print(
  source_row_counts,
  n = Inf
)

Calculate total:

sum(
  source_row_counts$rows
)

Compare with:

nrow(
  cbc_primary_1999_2018
)

Possible causes

  • a source was omitted;
  • a source was included twice;
  • filtering occurred before binding;
  • the wrong source list was used;
  • a supplementary source entered the primary list;
  • a source object was overwritten.

Problem 11: The join multiplies rows

Typical message

Each row in x is expected to match at most 1 row in y

or the merged row count is larger than the CBC row count.

Check CBC key uniqueness

cbc_premerge_duplicate_keys <-
  cbc_primary_1999_2018 |>
  dplyr::count(
    survey_cycle,
    SEQN,
    name = "occurrences"
  ) |>
  dplyr::filter(
    occurrences > 1
  )

Check Demographic key uniqueness

demographic_premerge_duplicate_keys <-
  demographics_1999_2018 |>
  dplyr::count(
    survey_cycle,
    SEQN,
    name = "occurrences"
  ) |>
  dplyr::filter(
    occurrences > 1
  )

Inspect both:

print(
  cbc_premerge_duplicate_keys,
  n = Inf
)
print(
  demographic_premerge_duplicate_keys,
  n = Inf
)

Confirm the join key

The intended join key is:

c(
  "survey_cycle",
  "SEQN"
)

Confirm the relationship

Use:

relationship = "one-to-one"

This causes the join to fail when the uniqueness assumption is violated.

Do not remove the relationship declaration

The declaration is a protective validation feature.

It should not be removed merely to make the join run.

Problem 12: Non-key columns overlap before the join

Typical message

Unresolved non-key column-name overlaps remain

Identify the overlaps

overlapping_nonkey_columns <- intersect(
  setdiff(
    names(
      cbc_for_merge
    ),
    merge_key
  ),
  setdiff(
    names(
      demographics_for_merge
    ),
    merge_key
  )
)

Inspect:

print(
  overlapping_nonkey_columns
)

Fix

Determine whether each overlap represents:

  • the same variable from two components;
  • different variables with the same name;
  • duplicated provenance metadata;
  • an accidental local column.

Rename component-specific provenance columns before joining.

Do not accept automatic suffixes without understanding the conflict.

Problem 13: A required analysis variable is missing

Typical message

The final dataset is missing required analytical variables

Check available variables

names(
  cbc_demographics_labelled
)

Search for a name fragment:

grep(
  "HGB",
  names(
    cbc_demographics_labelled
  ),
  value = TRUE,
  ignore.case = TRUE
)

Trace the variable through each stage

Check the imported CBC sources:

purrr::imap_dfr(
  primary_cbc_sources,
  function(
      data,
      dataset_id) {

    tibble::tibble(
      dataset_id = dataset_id,
      variable_present =
        "LBXHGB" %in%
          names(
            data
          )
    )
  }
)

Check the combined CBC dataset:

"LBXHGB" %in%
  names(
    cbc_primary_1999_2018
  )

Check the merged dataset:

"LBXHGB" %in%
  names(
    cbc_demographics_1999_2018
  )

Possible causes

  • the variable does not exist in one or more source cycles;
  • the wrong CBC file was used;
  • the variable was renamed;
  • it was removed during select();
  • a join conflict changed its name;
  • a source schema changed.

Problem 14: Variable labels disappeared

Typical symptom

attr(
  data$LBXHGB,
  "label"
)

returns:

NULL

Possible causes

  • the dataset was exported to CSV and reloaded;
  • a transformation removed attributes;
  • the variable was recreated;
  • a conversion stripped the label.

Check the RDS file

rds_data <- readRDS(
  "data/processed/cbc_demographics_labelled_1999_2018.rds"
)
attr(
  rds_data$LBXHGB,
  "label"
)

Remember

CSV does not preserve R variable-label attributes.

Use:

  • RDS for analytical metadata;
  • CSV for portability;
  • the variable dictionary for documentation.

Problem 15: A factor contains missing values unexpectedly

Typical symptom

A recoded variable such as:

sex

or:

survey_cycle_factor

contains NA even when the source variable is present.

Inspect the original and recoded values

data |>
  dplyr::count(
    RIAGENDR,
    sex,
    .drop = FALSE,
    name = "records"
  )

For cycles:

data |>
  dplyr::count(
    survey_cycle,
    survey_cycle_factor,
    .drop = FALSE,
    name = "records"
  )

Possible causes

  • a source code was omitted from the factor levels;
  • a label was misspelled;
  • whitespace is present;
  • the factor level order is incomplete;
  • the source code differs from the expected coding.

Do not replace unexpected values silently

Inspect and document them before changing the recode.

Problem 16: A validation check fails

Typical message

Final validation failed
Hemoglobin figure-data validation failed
Complete pipeline validation failed

Inspect the saved validation table

For example:

cat outputs/validation/complete_pipeline_validation.csv

Or in R:

validation_results <- readr::read_csv(
  "outputs/validation/complete_pipeline_validation.csv",
  show_col_types = FALSE
)
validation_results |>
  dplyr::filter(
    !passed
  )

Investigate the named check

Each validation row corresponds to a specific expectation.

Examples:

Final composite key is unique

Investigate duplicate keys.

All ten expected cycles are present

Investigate source coverage.

All expected figure files exist

Investigate figure creation or export.

Do not change FALSE to TRUE

Validation results must reflect the data.

Fix the underlying problem rather than editing the validation table.

Problem 33: The pipeline stops because one output manifest includes itself

Why this can happen

If output_manifest.csv already exists before the file list is created, the manifest may include the previous version of itself.

When rewritten, its hash and file size change.

Safer approach

Exclude the manifest file from its own input list:

output_manifest_path <- file.path(
  "outputs",
  "validation",
  "output_manifest.csv"
)
manifest_files <- setdiff(
  manifest_files,
  output_manifest_path
)

Then create and save the manifest.

This prevents self-referential output metadata.

Create a troubleshooting report

When a problem cannot be solved immediately, record it systematically.

Add this helper function to a temporary diagnostic script:

create_troubleshooting_record <- function(
    section,
    error_message,
    suspected_cause = NA_character_,
    action_taken = NA_character_,
    resolved = FALSE) {

  tibble::tibble(
    recorded_at_utc = format(
      Sys.time(),
      tz = "UTC",
      usetz = TRUE
    ),
    section = section,
    error_message = error_message,
    suspected_cause = suspected_cause,
    action_taken = action_taken,
    resolved = resolved
  )
}

Create a record:

troubleshooting_record <-
  create_troubleshooting_record(
    section =
      "Source acquisition",
    error_message =
      "Download failed for one source file",
    suspected_cause =
      "Incomplete network response",
    action_taken =
      "Deleted the incomplete file and repeated the download",
    resolved =
      TRUE
  )

Save it:

readr::write_csv(
  troubleshooting_record,
  file.path(
    "outputs",
    "validation",
    "troubleshooting_record.csv"
  )
)

Minimal information to collect before asking for help

Provide:

  1. the exact command you ran;
  2. the complete first error message;
  3. the last 30–50 lines of terminal output;
  4. the section of the pipeline where it failed;
  5. the result of pwd;
  6. the result of Rscript --version;
  7. the result of quarto --version when relevant;
  8. the relevant file path;
  9. whether the pipeline was run from a clean session;
  10. whether the problem is reproducible.

Avoid reporting only:

It does not work.

A disciplined recovery workflow

Use this sequence after a failure.

Step 1

Stop running later sections.

Step 2

Save the complete console output.

Step 3

Identify the first meaningful error.

Step 4

Confirm the working directory.

Step 5

Confirm the relevant input file or object exists.

Step 6

Inspect dimensions, names, classes, and key counts.

Step 7

Correct the underlying cause.

Step 8

Restart from a clean R process.

Step 9

Rerun the complete pipeline.

Step 10

Confirm all validations pass before rendering the website.

What not to do

Do not:

  • delete records without understanding them;
  • remove validation checks merely to continue;
  • convert every variable to character;
  • use distinct() as a universal duplicate fix;
  • join without key validation;
  • edit binary XPT files;
  • treat warnings as harmless automatically;
  • rename files without updating references;
  • change figure paths without checking Quarto location;
  • render the website before required figures exist;
  • describe unweighted results as national estimates.

Final troubleshooting checklist

Before concluding that the pipeline is broken, confirm:

Knowledge check

NoteWhy should the first meaningful error be fixed before later errors?

Later failures are often consequences of an earlier problem. Fixing the original failure may resolve several downstream errors automatically.

NoteWhy should duplicate keys not be resolved automatically with distinct()?

Repeated keys can represent repeat examinations, complementary records, exact duplicates, or conflicting observations. Their meaning must be investigated before records are removed.

NoteWhy might a PNG open correctly but fail to appear in Lesson 17?

The image path in the Quarto file may be incorrect, the filename may differ in capitalization, or the site may not have been rendered after the image was created.

NoteWhy can a script work interactively but fail with Rscript?

The interactive session may contain packages, functions, or objects that the script did not create itself. A clean Rscript run exposes those hidden dependencies.

NoteShould a failed validation check be removed to allow the pipeline to finish?

No. The failed check identifies an unmet analytical or structural expectation. The underlying cause should be investigated and corrected.
