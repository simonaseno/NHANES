Laboratory Component Catalog

Current, planned, and research-stage NHANES laboratory pipelines

Explore validated, developing, planned, and research-stage laboratory components within NHANES Laboratory Data with R.
Laboratory roadmap · scientific review · reproducible pipelines

A laboratory component enters the catalog before it becomes a trusted pipeline.

This catalog separates validated implementations from components that are under development, planned, or still require scientific investigation. A listing signals analytical interest—not automatic readiness for use.

1 validated Implemented and documented pipeline
5 planned Included in the current roadmap

Catalog purpose

The catalog distinguishes:

  • implemented pipelines;
  • active development work;
  • planned components;
  • components requiring scientific review;
  • components not yet formally assessed.

A component’s presence in the catalog does not mean that its pipeline has already been validated.

Status definitions

Validated

Release-ready

Implemented, tested, documented, and included in a formal release.

In development

Actively being built

Coding, validation, scientific review, or documentation is underway.

Planned

Accepted into the roadmap

Included in future development plans but not yet implemented.

Research required

Scientific review needed

Eligibility, methods, weights, record structure, or harmonization require further investigation.

Not yet assessed

Scope not yet reviewed

The component has not undergone formal technical or scientific assessment.

Component onboarding pathway

Every new component should pass through four broad stages.

1
Scope Define the component, cycles, research purpose, and analytical population.
2
Scientific review Assess eligibility, methods, units, record structure, and weights.
3
Implementation Build manifests, crosswalks, scripts, validation rules, and outputs.
4
Release Test, document, review, publish, and assign validated status.

Component onboarding requirements

1. Source manifest

Minimum fields:

  • component
  • survey_cycle
  • file_name
  • source_url
  • record_level
  • expected_key
  • analytic_role

2. Variable crosswalk

Minimum fields:

  • survey_cycle
  • source_variable
  • harmonized_variable
  • label
  • unit
  • method
  • decision
  • notes

3. Eligibility review

  • eligible ages;
  • sex restrictions;
  • pregnancy restrictions;
  • examination requirements;
  • fasting requirements;
  • subsample selection;
  • collection-session restrictions.

4. Laboratory-method review

  • specimen type;
  • instrument;
  • method;
  • laboratory;
  • detection limits;
  • quality-control notes;
  • corrections;
  • comparability decisions.

5. Weight guidance

  • candidate interview or MEC weight;
  • specialized subsample weight;
  • multi-cycle construction;
  • exclusions;
  • limitations.

6. Record-level contract

  • one record per participant;
  • multiple records per participant;
  • repeat examinations;
  • replicate measurements;
  • specimen-level records.

7. Validation rules

  • source-file existence;
  • HTTP success;
  • expected variables;
  • expected key;
  • key uniqueness where required;
  • cycle consistency;
  • row-count review;
  • missingness review;
  • join-contract testing.

8. Required outputs

  • processed RDS;
  • optional CSV;
  • provenance manifest;
  • validation summary;
  • duplicate report;
  • unresolved-conflict report;
  • package-version record;
  • session information.

How development priorities are selected

Public-health relevance Does the component support important clinical, epidemiological, or policy questions?
Cycle availability Is the component available across enough cycles to support useful analysis?
Methodological complexity Are methods, eligibility, weights, and harmonization manageable?
Learner demand Is there clear educational or analytical interest in the component?
Architectural fit Can the component use or extend the current pipeline structure?
Documentation quality Are official files, methods, eligibility notes, and weight guidance available?
Scientific collaboration Is suitable subject-matter expertise available for review?

Requesting a component

Before proposing a new laboratory pipeline, identify:

  • the desired laboratory component;
  • the survey cycles;
  • the primary research question;
  • required supporting variables;
  • the intended population;
  • whether weighted national inference is required.

Requests may be submitted through the project’s GitHub issue tracker.

Catalog limitations

WarningThis catalog is a roadmap, not an analytical authorization

It does not replace:

  • official NHANES component documentation;
  • laboratory methods documentation;
  • analytical guidelines;
  • current release notes;
  • cycle-specific scientific review;
  • expert judgment.

Page summary

A component becomes a validated pipeline only after it has passed through:

scope definition
scientific review
source mapping
variable harmonization
weight selection
record-level validation
reproducibility testing
documentation
release review

The catalog therefore distinguishes between:

interest
planning
research
implementation
validation

That distinction protects users from treating an analytical roadmap as a finished scientific product.
